# 2026-10-12 — 아트 방향과 Godot 감 잡기

어제(10/11) 끝낸 아트 출처 조사([art_source_research](../art_source_research/README.md))를 다시 보면서 나눈 대화다. 최종 결정은 여전히 10/18(WBS 2.14)이다.

## 1. 출발점 — 조사 보고서의 결론

- 권장안: Minifantasy Complete Bundle($69.99). 아트는 팩만, Claude는 코드만.
- 예비안: Ninja Adventure(CC0, 16px) + Claude 보충(시설·다크 팔레트).
- Claude 단독은 비권장. 이유 셋: 인간형 유닛 품질, 시간(중앙값 35~40h 추정), 스팀 AI 공개.
- 10/18 전에 반나절 시험(영웅 걷기 4프레임 + 들판 타일 1세트)으로 가린다([08](../art_source_research/08_half_day_trial.md)).

## 2. "도트 느낌으로 하고 싶은데 돈 써야 하나?"

- **아니다.** 후보 전부가 도트 픽셀이다. 무료 후보: Ninja Adventure(CC0), 0x72 DungeonTileset II(PWYW, CC0), Claude 단독.
- 다만 **0원이면서 AI 공개도 피하는 조합은 조사에서 못 찾았다.** 무료 16px 팩에는 탑·성벽 같은 시설이 없어서 그 빈 곳을 Claude가 그리면 공개 대상이 된다.
- 한글 도트 폰트(물마루, Galmuri)는 OFL이라 어느 안이든 0원.

## 3. 사용자 판단 — AI 공개를 피할 생각 없음

> "ai 공개 피할생각 없음. 애초에 개발을 바이브코딩으로 진행하니깐"

- **정정:** 바이브코딩 자체는 공개 대상이 아니다. 2026-01 스팀 문구에서 코드 도우미 같은 효율 도구는 빠졌다. 공개 대상은 Claude가 만든 **아트가 빌드에 들어갈 때**다([04 §1.2](../art_source_research/04_policy_and_rights.md)).
- 그래도 공개를 감수하면 결론은 같다. **Claude 단독 비권장 이유 셋 중 하나(공개)가 빠지고 품질·시간만 남는다.**
- 참고: 공개작은 리뷰 수가 약 52.6% 적다는 분석이 있다(상관관계). 숨겼다 드러난 사례는 반발이 더 컸다.

## 4. "16px 도트인데 Claude가 35시간이나 걸릴까?"

- 의심이 맞다. 35~40h는 **측정값이 아니라 가정을 쌓은 추정**이다(Q-25, 근거 없음으로 표시됨).
- 35~40h는 **아트 전체** 시간이다. 유닛 몫은 6~24h이고, 나머지는 Godot 적용(4~8h, 에셋팩이어도 듦), 재작업 여유, 시설·타일·이펙트·UI·캡슐, 파이프라인 준비다.
- 유닛 시간 가정: 종당 반복 10~20회 × 반복 1회 4~8분, 9종을 따로 셈.
- 줄 여지 (Claude 의견, 추론):
  - 16×16은 256픽셀이고 걷기는 "다리 행 교체 + 몸통 1px 오르내림" 차분이면 된다.
  - 영웅·용병 2·공병은 같은 몸 뼈대에 무기·색만 바꾸면 된다. 적 5종도 뼈대 2~3개로 묶인다.
  - 그러면 유닛 몫은 몇 시간, 전체는 대략 15~30h.
- **남는 위험은 시간보다 품질 수렴이다.** 느린 게 아니라 몇 번 고쳐도 원하는 수준에 못 닿는 것. 참고 사례에서 Claude는 결함 11건을 찾고 4건을 놓쳤다.
- 이 질문은 반나절 시험이 직접 잰다: U3(반복 1회 실제 시간), H7(영웅 기본 포즈+걷기를 몇 회 만에 끝내나, 상한 2h·6회). 영웅을 1시간 안에 끝내고 뼈대를 재사용할 수 있으면 35h는 과대 추정이다.

## 5. 사용자 판단 — 에셋 없이도 될 것 같다

> "내가 볼때도 별다른 에셋없어도 될꺼 같긴해"

- Claude 제작(에셋팩 없음) 쪽으로 기울어짐. 확정은 반나절 시험 뒤 10/18.

## 6. Godot 감 잡기 — 웹 개발(React·Spring·DB)에 대응하면

Godot 에디터 하나가 React·Spring·DB 역할을 다 한다. 1인용 게임이라 서버·DB가 없고 실행 파일 하나 안에서 돈다. 설치(4.7.2)와 `project.godot`은 이미 있다.

| 웹 | Godot |
|---|---|
| React 컴포넌트 | 씬(`.tscn`) — 노드 트리, 씬 안에 씬을 넣어 재사용 |
| DOM 트리 | 씬 트리(노드 트리) |
| props·state | 노드 속성, `@export` 변수 |
| 이벤트 콜백·emit | signal (`enemy_spawned.emit(e)`) |
| `useEffect`·생명주기 | `_ready()`, 매 프레임 `_process(delta)` |
| Spring 서비스 계층 | 순수 로직 스크립트 (`src/sim/battle.gd`) |
| 전역 store·싱글톤 Bean | Autoload |
| DB | `user://`에 JSON·ConfigFile 세이브 파일 (WBS 4.2) |
| `public/` | `res://` — PNG를 넣으면 자동 import |
| CSS·레이아웃 | Control 노드, Container, Theme |
| `npm run dev` | 에디터에서 F5 |
| Jest | `tests/eval/gd` (headless) |
| 빌드·배포 | Export → Windows `.exe` → Steam 업로드 (나중에) |

웹과 가장 다른 점:

1. **게임 루프.** React는 이벤트가 있을 때 다시 렌더하지만 게임은 초당 60번 `_process(delta)`가 돈다.
2. **에디터가 시각적.** 씬 파일은 텍스트라 Claude가 편집할 수 있지만, 배치는 에디터 화면으로 확인한다.

이 프로젝트는 이미 웹처럼 나뉘어 있다(`tests/eval/gd/lib.gd` 기준): `src/sim/battle.gd`(로직, 화면 없이 테스트) / `src/ui/controls.gd`(입력) / 화면은 sim 상태를 그리기만 한다. 그래서 아트는 마지막에 끼우는 부분이다 — PNG를 `res://`에 넣고 텍스처 필터를 Nearest로, `AnimatedSprite2D`에 연결.

감 잡기용: 공식 튜토리얼 "Your first 2D game"(Dodge the Creeps), 1~2시간.

## 7. 곁가지 — eval-gate 훅

- specgate `eval-gate` 훅이 대화를 끝낼 때마다 막는다(SG1048: 스냅샷 phase=red, stop은 final 요구).
- 원인은 대화 내용이 아니라 W1 평가 테스트가 동결된 채 red인 상태다. W1 구현이 green이 될 때까지 문서·조사 대화에서도 계속 뜬다.
- 스냅샷을 손으로 final로 바꾸는 건 속이는 것이라 하지 않았다.

## 8. "유닛·몬스터는 조금 입체적으로?" → B 방식 선택

입체감을 내는 길은 셋이었다.

| 방식 | 내용 | 판단 |
|---|---|---|
| A | 2D 도트 + 3/4 탑다운 음영·발밑 그림자 | 일정 영향 거의 없음 |
| **B** | 3D 형체를 코드로 만들어 고정 카메라로 도트 렌더 | **사용자 선택** |
| C | Godot 실시간 3D + 도트 셰이더 | 11/30 일정에 무리, 제외 |

> "b가 좋아보인다. 머리속에 그리는 이미지에 적 몬스터들이 성벽을 오르는 장면이 있어서 3d 풍도 좋아보인다. 스타크래프트도 탑뷰지만 3d 아님? 그런 느낌인거지"

- 스타크래프트 1이 정확히 B다. 3D 모델을 미리 렌더한 2D 스프라이트다. 실시간 3D는 스타크래프트 2(C에 해당).
- B의 장점: 방향·빛·프레임 일관성을 기하 계산이 맡는다. Claude가 가장 약한 부분을 피해 간다. 높이 축이 생겨 "성벽을 오르는" 그림과도 맞는다.
- B의 걱정: 유일한 선례(COMPASSO)는 48×64였는데도 눈·손·밴딩이 약했다. 16px에서는 더 뭉개질 수 있다 → 시험에서 16·24·32px를 같이 뽑아 본다.
- 반나절 시험(08)의 영웅 단계를 B로 바꿨다. 8방향(5 렌더 + 3 반전), H8 방향 일관성, H9 렌더 크기를 더했다. 총 4.5~5시간.

**열린 질문 — 성벽 오르기는 규칙인가 연출인가.** 지금 SPEC(S6~S9, S34)에서 적은 성벽을 **부수거나 돌아간다**. 오르는 규칙은 없고, 동결된 W1 평가 테스트도 그 전제다.
- 연출로만: 성벽을 공격하는 적이 성벽에 매달려 때리는 모습. 규칙은 그대로, 애니메이션 하나 추가.
- 규칙으로: 적이 성벽을 넘어온다. 길 찾기(S7)와 W1 테스트를 바꿔야 하는 큰 변경.

## 9. 성벽 오르기는 규칙으로 — 마을과 심장

> "규칙으로 두고 싶다. 왜냐하면 공중 몬스터도 생각하고 있다. 성벽을 넘으면 마을이 나오고 거기에 생산시설이나 주민 npc가 살고 있고 거기도 몬스터들이 공격할수있음 그 안쪽 마을 중앙에 지켜야할 보석?(아직 확정아님 어떤 형태인지) 심장? 같은게 파괴되면 패배하는 방식을 생각했음."

지금 SPEC과 맞춰 보면:

| 아이디어 | 지금 SPEC·WBS | 판단 |
|---|---|---|
| 중앙의 심장·보석, 파괴되면 패배 | 거점(S2)과 같다 | 이미 있음. 모양만 아트 결정 |
| 공중 몬스터가 성벽을 넘어온다 | 적 5종에 비행이 있다. U5 기본값 "경로 층 무시 → 구조물을 넘어 거점으로" | 이미 있음. U5 확정만 하면 된다 |
| 몬스터가 성벽을 오른다 | 없다. 적은 돌아가거나 부순다(S7~S9, S34) | **새 규칙** |
| 성벽 안 마을(생산 시설·주민 NPC)을 몬스터가 공격 | 없다. 맵은 열린 들판 + 자유 건설, 적은 구조물을 반격·길막·거점일 때만 친다(I7) | **새 규칙 + 출시 범위 추가** |

Claude 의견(추론):

- 오르기는 **특정 적 종류만**. 모든 적이 오르면 성벽 미로(이 게임의 바닥, W1 시험 대상)가 무의미해진다. S34가 이미 "성향은 적 종류마다 데이터 값"이라 오르기를 세 번째 성향으로 더하면 된다(오르기형의 성벽 칸 비용 = 체력과 무관한 오르는 시간). 기본 성향 적 기준인 W1 테스트(EV6·7·9)는 그대로 산다.
- 성벽은 지금처럼 플레이어가 짓고, 마을(집·주민)은 심장 주변에 미리 놓인 맵 요소로.
- 패배는 심장 하나로 두고, 마을 피해는 경제 손실(수입 감소)로. 근거: Bad North는 지켜 낸 집 수에 비례해 코인을 준다, DINO는 보호받지 못한 민간 확장이 습격의 먹잇감이 된다([03_resource_economy §7 ECO-07](../game_design_research/02_control_and_economy/03_resource_economy.md)).
- 주민은 규칙상 "집 건물의 수입"으로 단순화하고 돌아다니는 모습은 연출로 둔다.
- 오늘(10/12)이 WBS 1.3 출시 범위 확정일이다. 마을·오르기형은 범위 추가이고 R7(설계 변경으로 구현량 증가)에 얹힌다. 적 수를 늘리지 않으려면 5종 중 하나(예: 빠름)를 오르기형으로 바꾸는 안도 있다.

## 10. 성벽은 구조물이 아니다

> "성벽이랑 구조물이랑 다른거다. 구조물은 내가 설치하는거고 성벽은 기본적으로 존재하는거다. 물론 업그레이드는 가능하다."

- **어제 확정본과 충돌한다.** WBS 출시 범위 "성벽 1종, 격자 위 자유 배치", SPEC I1(구조물 = 타워·성벽·생산 시설), S10(준비 단계에 성벽을 놓으면 경로 재계산), 동결 테스트 EV5~EV10·EV15·EV35는 모두 성벽을 플레이어가 놓는다고 본다.
- **길 찾기 규칙은 그대로 산다.** S7(부술지 돌아갈지 비용 비교), S9(완전히 막히면 가장 싼 성벽을 부숨), S34(적 종류별 성향)는 누가 성벽을 놓았든 같다. 마을을 두른 성곽에 오히려 잘 맞는다 — EV7이 "거점을 성벽으로 둘러싸면 가장 약한 성벽을 부순다"이다. 업그레이드(체력↑)는 적이 더 약한 구간을 노리게 만들어 "어디를 보강할까"라는 판단을 낳는다(추론).
- 구현(추론): 성벽은 스테이지 데이터로 미리 놓고, `build("wall")`은 스테이지 배치·테스트 상황 만들기용으로 남긴다 → 동결 테스트는 고치지 않아도 된다. 고칠 것은 SPEC 문장(I1, S10, 출시 범위 표)과, 근거 해시가 바뀌는 EVAL 항목의 `## 개정` 한 줄(현재 evalFreeze 기본값 reason이라 허용).
- 열린 질문: 성벽 밖 들판에서 플레이어가 길을 막아 미로를 만드는 플레이가 남는가. 구조물(타워 등)은 I3에 따라 이미 길을 막는다.

## 11. 세 겹 방어 — 들판·성벽·마을

> "들판에 타워나 성벽(더미)를 건설할수있고 들판에만 건설할수 있게금 하려고 한다. 성벽에는 대포를 설치해야지. 그게 그림이 맞지않을까?"

| 겹 | 무엇이 있나 | 누가 만드나 |
|---|---|---|
| 들판 (1선) | 타워, 방벽(가칭 — 사용자 표현 "성벽(더미)") | 플레이어가 짓는다. 건설은 들판에서만 |
| 성벽 (2선) | 고정 성곽, 대포 | 처음부터 있다. 업그레이드 가능 |
| 마을 (3선) | 생산 시설, 주민 집, 중앙의 심장 | 처음부터 있다 |

Claude 의견(추론):

- 그림이 맞다. 겹마다 하는 일이 다르다 — 들판은 미로로 늦추고, 성벽은 버티며 쏘고, 마을은 뚫리면 잃는다.
- **W1이 그대로 산다.** 동결 테스트의 `build("wall")`은 들판 방벽이다. 미로·우회·부수기(S7~S10, EV5~EV10)가 문장 그대로 맞다. W1 시험 맵에는 성곽 없이 들판만 있어도 된다. 성곽·대포·마을·오르기는 W2·W3에 얹는다.
- SPEC에서 고칠 것: "성벽"을 들판 방벽과 성곽으로 나누는 용어, I1(구조물 정의), I24(건설 가능 칸 = 들판), 출시 범위 표.
- 오르기형이 성벽 위 대포를 노리게 하면 오르기 규칙에 이유가 생긴다(아이디어).

새로 생긴 질문:

- 성문: 마을의 생산 시설에서 나온 용병과 영웅이 들판으로 어떻게 나가나. 추천은 성문 칸(아군만 통과, 적에게는 성벽 칸과 같은 비용 규칙).
- 대포: 처음부터 달려 있나, 성벽 업그레이드로 사서 다나. 추천은 업그레이드("건설은 들판에서만"과 맞는다). 출시 범위의 공격 타워 3종 안에서 셀지 따로 셀지도 정한다.
- 생산 시설은 마을에 미리 있는 건물로 보고, 플레이어가 짓지 않는다(9절 발언 기준 — 확인 필요).

## 12. 성문과 성벽 위

> "성벽위에 대포를 설치할테니 그쪽으로도 이동이 가능하고 원거리 공격이 가능하면 거기서도 공격이 된다. 대문(정문)을 열어야 들판으로 이동가능. 양끝에 쪽문 만들어서 이동할수있게 하면 될듯. 이것도 여닫이로."

정리:

- 성벽 위는 아군이 올라갈 수 있는 자리다. 대포는 플레이어가 성벽 위에 설치한다(건설 구역: 들판 = 타워·방벽, 성벽 위 = 대포).
- 원거리 유닛은 성벽 위에서 들판의 적을 공격한다.
- 문은 셋: 정문 1 + 양 끝 쪽문 2. 모두 여닫이. 문을 열어야 마을 ↔ 들판 이동이 된다.

Claude 의견(추론):

- 조사에 근거가 있다. [02_garrison_and_fortification](../game_design_research/01_rules_architecture/02_garrison_and_fortification.md)의 GAR-04는 관문을 "아군 통로 + 성벽 위로 오르는 접근점 + 사격 위치"로 두고 접근점을 하나에 몰지 말라고 한다. 문 셋이 성벽 위로 오르는 계단을 겸하면 그대로 맞는다.
- **열린 문으로 적도 들어오게 하자.** S7 비용 규칙에서 열린 문은 비용 0인 칸이라 적이 자연히 그쪽으로 몰린다. "출격하려면 문을 열어야 하고, 열면 위험하다"는 긴장이 규칙 하나 없이 생긴다. 닫힌 문은 체력 있는 성벽 칸으로 다룬다.
- 범위: 출시 범위 표는 "주둔"을 뺐다. 성벽 위 이동·사격은 가벼운 주둔이라 범위 추가다. 문 여닫기 조작(UI)도 더해진다. R7에 얹힌다.
- W1 영향 없음(성곽은 W2 이후).

## 13. 대포는 공병이, 생산 시설은 해금으로

> "대포는 공병이 설치해야함. 대포는 성벽이나 들판 어디든 건설은 가능하도록."
> "생산시설은 해금 느낌으로 진행하면 되겠다. 레벨오를수록 건설가능한 생산시설이 추가되는 느낌으로다"

정리:

- 대포는 구조물이다. 공병이 짓는다. 성벽 위와 들판 어디에나 지을 수 있다.
- 생산 시설은 플레이어가 짓는다(11절의 "마을에 미리 있음" 추정은 틀렸다). 레벨이 오르면 지을 수 있는 생산 시설 종류가 늘어난다.

건설 구역(지금까지 기준):

| 구역 | 지을 수 있는 것 |
|---|---|
| 들판 | 타워, 방벽, 대포 |
| 성벽 위 | 대포 |
| 마을 | 생산 시설(확인 필요) |

Claude 의견(추론):

- 대포를 공격 타워 3종 중 하나("성벽 위에도 놓을 수 있는 타워")로 세면 출시 범위가 늘지 않는다.
- 지금 SPEC은 준비 단계 건설은 즉시(S18, EV35), 전투 중 건설은 공병(S22)이다. 대포도 같은 규칙이면 새 규칙이 필요 없다.
- 생산 시설 종류를 용병 종류(전투 용병 2 + 공병)에 맞추면 해금 대상이 셋이라 범위가 크게 늘지 않는다.
- 생산 시설이 마을에 있으면 "마을 피해의 대가"(5번 질문)가 저절로 생긴다 — 생산 시설이 부서지면 그 용병을 못 뽑는다.
- "레벨"의 뜻이 셋으로 갈린다: 스테이지 진행(클리어할수록 해금), 판 안의 마을 레벨(골드로 올림), 계정 레벨. 출시 범위는 "육성 트리", "캠페인 결산"을 뺐다. 스테이지 진행 해금이 가장 가볍다(진행 저장은 이미 범위 안).

## 14. 문·오르기·마을 피해 확정

> "1: 네, 4: 네. 어지간해서는 성문을 부수고 들어오려고 하는데 일부 유닛은 기어오름. 5. 그것도 좋은 아이디어 같다."

- 열린 문으로 적도 들어온다.
- 대부분의 적은 성문을 부수고 들어오고, 일부 종류만 성벽을 기어오른다.
- 마을의 생산 시설이 부서지면 그 시설의 용병을 못 뽑는다.

Claude 의견(추론):

- "어지간해서는 성문"은 새 규칙 없이 된다. 성문 체력을 성벽보다 낮게 두면 S9(가장 싼 성벽을 부숨)가 성문을 고른다. 플레이어가 성문을 보강하면 적은 다음으로 약한 성벽 구간으로 옮겨 간다 — "어지간해서는"과 맞는다.
- 어느 적이 오를지는 3.1에서 적 5종의 역할(SPEC I34)을 정할 때 고른다.

## 15. 마을 레벨·세금·대포 이동

> "1:마을 레벨이 좋아 보인다. 2:주민이 세금 내는 방식으로해서 수익이 줄어들면 되겠다. 3:준비단계에서는 즉시 생산가능. 대포는 타워랑 달리 공병대가 라운드 진행중에 위치를 이동시킬수 있음. 근데 카테고리틑 타워에 넣어도 될듯? 헷갈리려나? 이거는 추천해줘"

- 생산 시설 해금은 판 안의 마을 레벨로 한다.
- 주민이 세금을 낸다. 주민·집이 피해를 입으면 세수가 준다.
- 준비 단계에는 건설·생산이 즉시 된다(지금 S18과 같다).
- 대포는 전투 중에 공병이 위치를 옮길 수 있다. 타워는 못 옮긴다.

Claude 추천 — 대포의 분류: **규칙에서는 별도 종류, 플레이어 화면에서는 같은 묶음.**

- 규칙(SPEC)에서는 대포를 타워와 다른 종류로 둔다. 놓을 수 있는 곳(성벽 위 + 들판)과 이동 가능 여부가 다르기 때문이다.
- 건설 메뉴에서는 한 탭에 같이 둔다. 탭 이름은 "타워" 대신 "공격 시설"로 하면 대포가 섞여도 헷갈리지 않는다. 출시 범위는 "공격 시설 3종 = 타워 2 + 대포 1"로 세면 늘지 않는다.
- 헷갈림은 이름보다 놓을 수 있는 칸을 보여 주는 것으로 푼다 — 건설 중에 지을 수 있는 칸을 강조 표시.

Claude 의견(추론):

- 마을 레벨은 조사의 "확장·수입 투자 대 최종 방어선 보험" 딜레마와 맞는다([03_resource_economy](../game_design_research/02_control_and_economy/03_resource_economy.md) 91행 부근). 골드를 마을 레벨에 쓸지 지금 방어에 쓸지가 매 준비 단계의 선택이 된다.
- 세금은 준비 단계 시작마다 살아 있는 집 수에 비례해 걷는 것이 가장 단순하다(Bad North의 "지켜 낸 집 수에 비례한 코인"과 같은 구조).
- 대포 이동은 새 메커니즘이다. 가장 단순한 형태는 "공병이 가서 철거 → 새 칸에 다시 설치(시간 듦, 비용 없음)"이고, 이동 중 공병이 죽으면 S24(미완성 구조물)를 그대로 따른다.

### 범위 점검 (추론)

오늘 새로 생긴 시스템: 성곽·성문 여닫기, 성벽 위 이동·사격, 오르기형, 대포 이동, 마을 레벨, 생산 시설 3종 해금, 세금. W1은 그대로지만 W2·W3 몫이 크게 는다(WBS R7). 일정이 밀릴 때 빼는 순서 후보: 대포 이동 → 쪽문(정문만) → 마을 레벨(생산 시설 처음부터 전부) → 성벽 위 이동.
