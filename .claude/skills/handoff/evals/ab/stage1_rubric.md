## 3. 실행

```
cd <경로> && claude -p "<프롬프트>" --model claude-opus-5-5 --permission-mode plan \
  --disallowedTools AskUserQuestion "Bash(git push:*)" "Bash(gh:*)" [B만 "Skill(handoff)"] \
  --settings <격리 훅> --output-format stream-json --verbose
```

- **프롬프트**(계획서 §4): A는 `/handoff resume`이고, B는 `다음 작업: <메모>. 진행해.`이다. 메모는 오타까지 그대로 쓴다.
- **설정**: effort는 사용자 설정 그대로 xhigh다. 훅·플러그인(ponytail·specgate·알림)도 사용자 설정 그대로이며, 모든 조건에 같다.
- **질문 처리**: `AskUserQuestion`은 끈다. 그래서 질문은 계획 글 안에 나온다.
- **순서**: 12개 실행(지점 × 조건 × 회차)을 시드 20261014로 섞은 순서로 돌린다.
- **실패 처리**: 오류로 끝났거나 계획 글이 없으면 같은 조건으로 한 번 더 돌린다. 그래도 실패하면 결측으로 적고 결과 보고에 따로 쓴다.
- **실제 세션과의 차이**: 실제 세션은 Claude Code 2.1.296의 auto 모드였고, 실험은 2.1.299의 plan 모드다. 원격·`gh`·질문 도구가 없다는 점도 다르다. GitHub 상태는 두 조건 모두 볼 수 없다. A는 NAP에 적힌 PR 상태를 알고, B는 main에 들어가지 않은 커밋으로 앞 작업이 남았음을 알 수 있다.

## 5. 채점표

항목마다 충족이면 1, 아니면 0이다.

- 기본: 계획 글에 그 내용이 있으면 충족이다.
- «묻는다»(g4): 사용자에게 묻거나, 기본안을 내고 확인받겠다고 적었으면 충족이다. Claude가 혼자 정해 버렸거나 언급이 없으면 불충족이다.
- «~하지 않는다»(g3·g5): 어긋나는 제안이 없으면 충족이다. 언급이 없어도 충족이다.

정답의 출처는 NAP가 아니다(§6 단계 1의 3). 출처는 다섯 가지다.
- g1: 사용자 메모와 실제로 이어진 커밋
- g2: 그 시점 저장소
- g3: 앞 세션의 사용자 발화
- g4: 다음 세션에서 사용자가 실제로 답한 질문
- g5: 단계 0의 X(틀린 항목)

시각은 KST다.

## 6. 채점과 판정

1. **채점**: 실행마다 채점 에이전트를 하나씩 둔다. 에이전트는 조건을 모른다. 입력은 그 지점의 상황 설명·채점표·가린 계획 글이고, 출력은 항목마다 0이나 1과 그 근거가 된 계획 글 인용이다.
2. **사용자 확인**: 사용자가 두 묶음을 확인하고, 고친 판정을 쓴다.
   - 무작위 20%(시드 20261014)
   - A·B 판정이 갈린 항목 전부. 지점·항목마다 A 2회와 B 2회의 충족 수가 다르면 갈린 것이다. 단계 0에서 무작위 표본(0/20)은 G0를 정하는 항목의 부풀림(6/18)을 잡지 못했다.
3. **집계**: 순서는 넷이다.
   - 실행 점수 = 충족 항목 수 / 그 지점 항목 수(g3-확장 제외)
   - 조건·지점마다 2회 평균을 낸다
   - 지점마다 A 평균 − B 평균을 낸다
   - A−B = 지점 3곳 값의 평균
4. **판정**(§7 단계 1): A−B ≥ 0.25면 효과 있음이다. 그 밖은 쓸모없음이다. 0.10 이하는 G1 «경계 인계에서 무용»이고, 0.10과 0.25 사이도 입증 책임에 따라 쓸모없음이다. 해로움은 이렇게 정한다: A가 g5를 한 번이라도 어기고 B는 한 번도 어기지 않은 지점이 2곳 이상이다.
5. **g3-확장**(`2026-10-13/r1` g3-1): 판정에 넣지 않고 지점별 충족 수(A x/2, B y/2)를 따로 보고한다. A가 B보다 많이 충족하면, G1이 «무용»이어도 단계 2에서 S1(말로만 정한 결정이 있는 경계 인계)을 빼지 않는다. S1은 이 정보를 끝까지 재는 유일한 곳이기 때문이다.
