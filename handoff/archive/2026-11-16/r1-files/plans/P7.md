## 2. 동작 명세

### 2.1 버킷 — 바뀌는 것은 «보는 몸 수»뿐이다

- 대상 세 곳:
  - `_target_of(e)`: 적 e가 노릴 유닛을 `units`에서 고르는 루프.
  - `_nearest_enemy(from, reach, …)`: 유닛·쏘는 구조물이 `enemies`에서 가장 가까운 적을 고르는 루프.
  - `_shove(e, by, bodies)`: 움직이는 몸이 상대 편 몸(`units` 또는 `enemies`)에 막혀 자리를 고치는 루프.
- 규칙 R1(후보): 한 점 p와 거리 r로 물으면 «p에서 r + 그 몸의 반지름 안에 있는 몸»은 **빠짐없이** 후보에 든다. 더 드는 것은 괜찮다. 후보는 배열 번호의 오름차순이다.
- 규칙 R2(같은 결과): 세 루프는 본문을 그대로 두고 후보만 돈다. 후보에서 빠진 몸은 원래 루프에서도 거리 조건에 걸려 아무 일도 하지 않았을 몸이다. 그래서 고른 대상, 같은 거리일 때의 승자(`_target_of`는 배열 앞쪽, `_nearest_enemy`는 배열 뒤쪽), `_shove`가 몸을 하나씩 차례로 밀어 얻는 자리가 모두 같다.
- 규칙 R3(낡지 않음): 버킷은 편마다 하나다(아군 `_ub`, 적 `_eb`). 그 편의 누군가 생기거나, `pos`·`radius`가 바뀌거나, 배열 크기가 달라졌으면 다음 물음 때 통째로 다시 담는다. 스텝 안팎을 가리지 않는다.
- 규칙 R4(큰 몸): 반지름이 1칸(`BUCKET_BIG`)을 넘는 몸(슬라임 킹 2.0, 원정 보스 몸 1.2~3.0)은 버킷에 넣지 않고 늘 후보다.
- 규칙 R5(`_shove`의 다시 뽑기): 처음 자리 `at`에서 «움직이는 몸의 반지름 + SHOVE_SLACK»으로 후보를 뽑는다. 몸에 밀려 p가 `at`에서 SHOVE_SLACK보다 멀어지면 그 p에서 다시 뽑고, 이미 지난 번호는 건너뛴다. 줄지어 선 몸을 따라 멀리 미끄러져도 원래 루프와 같다.
- 규칙 R6(다 보는 길): `bodies`가 `units`·`enemies`가 아닌 배열(`[]`, 시험이 넘긴 배열)이거나, 물은 거리가 유한하지 않거나 32칸을 넘거나, `scan_all`을 켠 판(옛 길, 동치 평가·성능 비교용)이면 모든 번호를 본다. 그 밖에는 늘 후보를 줄인다: 훑을 버킷 칸이 몸이 든 칸보다 많지 않으면 칸을 하나씩 찾고, 많으면 몸이 든 칸을 돌며 범위 안인 칸만 모은다. (검증에서 고침: 처음 안은 «훑을 칸이 몸이 든 칸 + 9보다 많으면 모든 번호»였다. 몸이 뭉칠수록 든 칸이 적어 전수로 돌아가므로, P6 대열 전의 뭉친 싸움에서 버킷이 헛돈다 — §3.1 (나) 아래 수치)
- 버킷 크기 2칸·큰 몸 기준·여유(PAD)·SLACK은 행동에 닿지 않는다. 빠르기만 바꾼다.

## 3. 코드 변경

### 3.0 먼저 확인(0단계, 스크래치 5분)

이 설계는 «안쪽 클래스의 `static var`»와 «setter»에 기댄다. Godot 4.7.2에서 돌려 본 것이 아니다 [추론]. 스크래치 스크립트로 먼저 본다.

```gdscript
extends SceneTree
class A:
	static var n := 0
	var pos: Vector2:  # 선언 줄 끝의 주석도 그대로 둘 수 있나
		set(v):
			pos = v
			n += 1
	func _init() -> void:
		pos = Vector2.ZERO  # ① _init 안 대입(Unit·Enemy의 _init이 이렇게 쓴다)
func peek() -> int:
	return A.n  # 바깥 클래스 함수에서 읽기(_units_near가 Unit.stir를 읽는 꼴)
func _initialize() -> void:
	var a := A.new()
	a.pos = Vector2.ONE  # ② 타입 붙은 변수
	a.pos += Vector2.ONE  # ③ 더해 넣기
	a.set("pos", Vector2.ZERO)  # ④ set()(save.gd#_put, battle.gd#_come_home, tuning.gd#_match)
	a.pos.x = 3.0  # ⑤ 성분 쓰기
	var v = a  # ⑥ 타입 없는 변수(battle.gd의 `for m in bodies`, `var e = …`)
	v.pos = Vector2.ONE
	print(peek(), " ", a.get_property_list().filter(func(p): return p.usage & PROPERTY_USAGE_SCRIPT_VARIABLE).map(func(p): return p.name))
	quit()
```

- 기대: `6 ["pos"]`. 여섯 가지 쓰기가 모두 setter를 지나고, 인스턴스 속성 목록에 `n`이 없다. (검증에서 더함: `_init` 안 대입, 타입 없는 변수, 바깥 클래스 함수에서 읽기. 이 파일의 안쪽 클래스가 속성 접근자를 쓰는 선례는 `Unit.present`·`Villager.hp`의 getter다 — setter와 안쪽 클래스 static var는 선례가 없다)
- 봇의 코드 생성 하위 클래스도 본다(버킷 커밋 뒤, 스크래치): `GDScript.new()`에 `extends "res://src/sim/battle.gd"`와 `func _target_of(e: Enemy): return super(e)`를 넣어 `reload()`한 클래스로 시험 스테이지 판을 만들고, 병사 하나·적 하나를 두어 20스텝 돌린 뒤 오류가 없고 그 판의 `_ub.stamp`가 `Unit.stir`와 같은지 본다(`tools/balance/autoplay.gd#_battle_class`와 같은 꼴. 봇 판을 돌리는 것이 아니다).
- 목록에 `n`이 나오면: `save.gd#SKIP`과 `battle.gd#_body`의 제외 목록에 세대 수 이름을 넣는다(안 넣으면 저장·원정 되돌리기가 세대 수를 옛 값으로 되돌려 낡은 버킷이 «맞다»고 읽힌다).
- 안쪽 클래스의 static이 안 되면: 새 파일 `src/sim/stir.gd`(`static var u := 0`, `static var e := 0`)를 두고 battle.gd에 `const Stir := preload("res://src/sim/stir.gd")`, setter에서 `Stir.u += 1`. 안쪽 클래스는 바깥 상수를 본다(`CostGrid`가 `UPGRADE_MULT`를 쓰는 것과 같다). 새 `.gd`는 `.uid`도 만든다.

### 3.1 `src/sim/battle.gd` — 버킷

(가) `class Enemy`·`class Unit`: `pos`·`radius` 선언에 setter, 클래스에 세대 수.

```gdscript
class Enemy:
	static var stir := 0  # 적이 생기거나 자리·몸 반지름이 바뀔 때마다 오른다(I+1). 판이 적 버킷이 낡았는지 이 값으로 본다
	var kind: String
	var pos: Vector2:  # 칸 단위, 칸 (x,y)의 중심 = Vector2(x,y)
		set(v):
			pos = v
			stir += 1
	…
	var radius: float:  # 몸 반지름(칸 단위)
		set(v):
			radius = v
			stir += 1
```

`Unit`도 같다. 새 인스턴스 변수는 두지 않는다(저장 사전의 꼴이 그대로여야 EV306이 그대로 통과한다).

(나) 새 블록 — **파일 맨 끝**에 둔다(상수·안쪽 클래스·변수·함수 모두. 앞 줄 번호가 덜 밀려 §3.1 대조가 가볍다).

```gdscript
# ── 2칸 버킷(I+1): 보는 몸 수만 줄이고 결과는 전수와 같다 ──
const BUCKET := 2.0  # 버킷 한 변(칸)
const BUCKET_BIG := 1.0  # 몸 반지름이 이보다 크면 버킷에 넣지 않고 늘 후보다(슬라임 킹·원정 보스 몸)
const BUCKET_PAD := 0.05  # 부동소수 여유(칸). 후보를 넓게만 잡는다
const SHOVE_SLACK := 1.0  # _shove가 후보를 다시 뽑지 않고 밀려도 되는 거리(칸)
const NOBODY := []

class Near:
	var cells := {}  # Vector2i(버킷 칸) → 그 칸에 든 몸의 배열 번호(오름차순)
	var big := []  # 큰 몸의 번호
	var rmax := 0.0  # 버킷에 든 몸의 가장 큰 반지름
	var stamp := -1  # 담은 때의 세대 수
	var n := -1  # 담은 때의 배열 크기

var _ub := Near.new()  # 아군(units)
var _eb := Near.new()  # 적(enemies)
var scan_all := false  # 참이면 버킷 없이 모든 몸을 본다(옛 길). 동치 평가와 성능 비교가 켠다
var audit = null  # 시험이 [0, 0, 0, 0]을 넣으면 물을 때마다 전수와 견줘 [물은 횟수, 놓친 몸 수, 후보 수 합, 전체 수 합]을 센다

func _units_near(p: Vector2, r: float) -> Array:
	return _near(_ub, units, Unit.stir, p, r)

func _foes_near(p: Vector2, r: float) -> Array:
	return _near(_eb, enemies, Enemy.stir, p, r)

# arr에서 «p에서 r + 그 몸의 반지름» 안에 있는 몸의 번호를 빠짐없이, 오름차순으로. 더 들어 있을 수 있다
func _near(ix: Near, arr: Array, stir: int, p: Vector2, r: float) -> Array:
	if scan_all:
		return range(arr.size())
	if ix.stamp != stir or ix.n != arr.size():  # 누가 움직였거나 들고 났다: 다시 담는다
		ix.cells.clear()
		ix.big.clear()
		ix.rmax = 0.0
		for i in arr.size():
			var m = arr[i]
			if m.radius > BUCKET_BIG:
				ix.big.append(i)
				continue
			ix.rmax = maxf(ix.rmax, m.radius)
			var k := Vector2i((m.pos / BUCKET).floor())
			if ix.cells.has(k):
				ix.cells[k].append(i)
			else:
				ix.cells[k] = [i]
		ix.stamp = stir
		ix.n = arr.size()
	var reach := r + ix.rmax + BUCKET_PAD
	var ids: Array
	if not is_finite(reach) or reach > 32.0:
		ids = range(ix.n)
	else:
		var a := Vector2i(((p - Vector2(reach, reach)) / BUCKET).floor())
		var b := Vector2i(((p + Vector2(reach, reach)) / BUCKET).floor())
		ids = ix.big.duplicate()
		if (b.x - a.x + 1) * (b.y - a.y + 1) <= ix.cells.size():  # 훑을 칸이 더 적다: 칸을 하나씩 찾는다
			for y in range(a.y, b.y + 1):
				for x in range(a.x, b.x + 1):
					ids.append_array(ix.cells.get(Vector2i(x, y), NOBODY))
		else:  # 몸이 든 칸이 더 적다(몸이 뭉쳐 있다): 든 칸을 돌며 범위 안인 칸만 모은다. 모든 번호로 돌아가지 않는다
			for k in ix.cells:
				if k.x >= a.x and k.x <= b.x and k.y >= a.y and k.y <= b.y:
					ids.append_array(ix.cells[k])
		ids.sort()  # 칸 안은 오름차순이지만 칸끼리는 섞인다
	if audit != null:
		audit[0] += 1
		audit[2] += ids.size()
		audit[3] += arr.size()
		for j in arr.size():
			if p.distance_to(arr[j].pos) <= r + arr[j].radius:
				var at := ids.bsearch(j)
				if at >= ids.size() or ids[at] != j:
					audit[1] += 1
	return ids
```

- 버킷 칸 열쇠는 담을 때와 물을 때 같은 식(`(자리 / BUCKET).floor()`)이다. 물을 때는 `reach`만큼 넓힌 정사각형이 걸치는 칸을 모두 본다. `floor`가 단조라 «거리 ≤ r + 반지름»인 몸의 칸은 그 안이다. PAD는 float32 거리 계산의 끝자리 오차를 덮는다.
- 수치(2.0·1.0·0.05·1.0·32)와 칸 훑기·든 칸 돌기를 가르는 기준은 행동과 무관하다. §7.4 step 시간으로 고를 수 있다(SLACK 0.5, 정수 열쇠 등). 바꿔도 EV는 그대로 통과해야 한다.
- **검증에서 고친 곳과 근거**: 처음 안은 «훑을 칸 > 몸이 든 칸 + 9»이면 `range(ix.n)`(모든 번호)을 돌려줬다. 저장소 밖 Python 스크래치(`plans/P7_check/bucket_fuzz.py`, float32 흉내)로 물음마다 후보 수 ÷ 그 편 몸 수를 셌다 [계산, Godot 실행 아님].

(다) `#_target_of` — 유닛 루프 두 군데만.

```gdscript
	# 전: for m in units:
	for i in _units_near(e.pos, maxf(sight, e.radius + 0.01)):
		var m = units[i]
		var d := e.pos.distance_to(m.pos)
		if d >= best_d and (d >= far_d or m.range < ranged):  # 거리 가지치기를 먼저(읽기만 하는 _free·_carried보다 싸다)
			continue
		if not _free(m, e) or _carried(m):
			continue
		…(뒤 조건문과 best·far 갱신은 그대로)
```

- 물은 거리의 근거: 본문이 반응하는 조건은 `d <= sight` 또는 `d <= e.radius + m.radius + 0.01`뿐이다.
- 차례를 바꾼 두 `continue`는 모두 읽기만 한다(`_free`는 `e.engaged`·`_holds`, `_carried`는 `fx`). 그래서 차례가 결과에 닿지 않는다.
- 돌진·결투·공성탑·열기구·비행선·공성·도발·원정 보스 가지와 마을 구조물·주민 루프, `_engage`, `_gate_or_base`는 그대로다. 서명도 그대로다(봇이 덮어쓴다).

(라) `#_nearest_enemy` — 루프 머리만.

```gdscript
	# 전: for e in enemies:
	for i in _foes_near(from, maxf(reach, body + 0.01 if body > 0.0 else 0.0)):
		var e = enemies[i]
		…(본문 그대로)
```

- 근거: 반응 조건은 `d <= reach` 또는 `touch`(`body > 0`이고 `d <= body + e.radius + 0.01`)다.

(마) `#_shove` — 몸 루프를 번호 루프로. 본문(겹침 판정·바깥 자리·아군의 둘레 돌기)은 글자 그대로 옮긴다.

```gdscript
func _shove(e, by: Vector2, bodies: Array) -> void:
	var mine: bool = is_same(bodies, units) or is_same(bodies, enemies)
	for v in [by, Vector2(by.x, 0), Vector2(0, by.y)]:
		var p: Vector2 = e.pos + v
		var at := p  # 후보를 뽑은 자리
		var ids: Array = _pick(bodies, at, e.radius + SHOVE_SLACK) if mine else range(bodies.size())
		var k := 0
		while k < ids.size():
			var i: int = ids[k]
			k += 1
			var m = bodies[i]
			…(원래 본문: gap · 겹침이면 p를 몸 바깥으로 · 아군은 둘레로)
			if mine and p.distance_to(at) > SHOVE_SLACK:  # 밀려서 훑은 범위를 벗어났다: 그 자리에서 다시 뽑고 지난 번호는 건너뛴다
				at = p
				ids = _pick(bodies, at, e.radius + SHOVE_SLACK)
				k = ids.bsearch(i + 1)
		…(칸 검사와 e.pos = p는 그대로)
```

- `_pick(bodies, p, r)`은 `_units_near` 또는 `_foes_near`를 고르는 한 줄짜리다(이름은 구현에서 정한다. `_bump`는 이미 있는 함수라 쓰지 않는다).
- `scan_all`이면 `_near`가 모든 번호를 주고, 그때 다시 뽑아도 결과가 같다.
- `_push_apart`는 고치지 않는다. `_part`가 넘기는 `others`가 `units`·`enemies` 그 객체라 `is_same`에 걸린다. `ground`(거른 사본)는 `bodies` 쪽이고 `_shove`에 가지 않는다.
- `_bulldoze`와 pathing 평가가 넘기는 `[]`는 다 보는 길(빈 루프)이다.

(바) 넣지 않는 것: 배열을 바꾸는 줄마다 세대 수를 올리는 줄. 부록 A의 표대로 지금 코드는 모든 길이 setter나 배열 크기에 걸린다. 대신 I+1 주석 한 덩어리에 «`units`·`enemies`에 이미 있던 몸을 `pos`를 안 건드리고 뺐다가 같은 수만큼 넣는 코드를 새로 쓰면 `Unit.stir += 1`을 함께 쓴다»를 적는다.

### 6.3 유닛 시험(새 파일 `tests/unit/gd/test_near_buckets.gd`)

- `test_candidates_cover_brute_force`: 씨앗 고정 난수로 몸 80개(반지름 0.18~0.9, 큰 몸 2.0 둘, 음수 자리와 x 64 넘는 자리 포함)를 놓은 판 200개에서, 무작위 점·거리로 `_foes_near`·`_units_near`를 물어 «거리 ≤ r + 반지름»인 번호가 모두 들고 오름차순인지.
- `test_shove_matches_full_scan`: 무작위 판 300개에서 같은 몸·같은 `by`로 `_shove`한 자리가, 그 몸을 제자리로 돌리고 같은 판에서 `scan_all`을 켜고 `_shove`한 자리와 같다(판을 둘 만들지 않는다 — 다른 판을 만들면 세대 수가 올라 낡음이 가려진다). 한 줄로 붙어 선 몸 12개를 따라 미끄러지는 판(다시 뽑기), 큰 몸에 닿는 판도 넣는다.
- `test_target_ties_keep_array_order`: 적에서 같은 거리에 선 유닛 둘 가운데 `_target_of`는 배열 앞쪽, 유닛에서 같은 거리의 적 둘 가운데 `_nearest_enemy`는 배열 뒤쪽을 고른다(둘 다 `scan_all`을 켠 답과 같다). 두 몸은 서로 다른 버킷 칸에 두되 배열 앞쪽 몸을 남동쪽 칸에 둔다(칸을 훑는 차례와 배열 차례가 거꾸로라, 후보를 번호순으로 안 고르면 갈린다).
- `test_stale_after_outside_write`(검증에서 더함): 한 판에서 먼저 물어 버킷을 담아 둔 뒤 ㉠ `pos` 대입 ㉡ `pos.x` 쓰기 ㉢ `set("pos", …)` ㉣ `radius` 대입 ㉤ 유닛 하나를 `units.erase`로 빼고 새 유닛을 넣기(수가 같다), 저마다 멀리 있던 몸을 물음 범위 안으로 들이는 꼴로 하고(나가는 쪽은 낡아도 틀리지 않는다), 바로 뒤에 `_units_near`·`_foes_near`가 전수로 고른 번호를 모두 담는다.

### 7.3 동치 검증(«행동이 그대로»의 증명)

다섯 겹이다. ①②는 저장소에 남고 ③④⑤는 스크래치다. 겹마다 증명하는 것이 다르다(검증에서 나눠 적음).

| 겹 | 증명하는 것 | 못 보는 것 |
|---|---|---|
| ① 저장소 평가 EV+1·EV+2, 유닛 시험 넷 | 버킷으로 고른 결과 = 전수로 고른 결과(새 본문끼리). 밖에서 바꾼 뒤 낡지 않음 | `_target_of`의 가지치기 차례 바꿈(두 쪽 다 새 본문이다). EV+1은 판이 둘이라 스텝 사이의 낡음이 가려진다(§2.3) |
| ② 본문 diff | 세 루프의 본문이 글자 그대로다(바뀐 곳은 `_target_of`의 `continue` 차례 하나) | 실행 결과 |
| ③ 스크래치 전후 비교(부록 B) | 옛 코드 = 새 코드(setter·가지치기 차례·버킷 모두). 프로세스에 판 하나라 낡음이 가려지지 않는다 | 시나리오에 없는 길 |
| ④ 스크래치 «두 번 돌려 견주기» | 평가 1,100여 개와 부록 B 시나리오가 거치는 모든 `_target_of`·`_nearest_enemy`·`_shove` 호출에서 버킷 = 전수 | 옛 본문과의 차이(③이 본다) |
| ⑤ 망가뜨려 보기 | ①의 시험이 버그를 실제로 잡는다 | — |

1. 저장소 평가 EV+1(`scan_all` 판과 스텝마다 견줌 + 후보 감사), EV+2(낡은 버킷), 유닛 시험 넷(§6.3).
2. 구조: 루프 본문을 그대로 두었다(§3.1). 리뷰에서 diff로 본문이 같은지 본다. 본문에서 바뀌는 곳은 `_target_of`의 가지치기 차례 하나뿐이다. `scan_all` 판도 그 바뀐 본문을 쓰므로 이 차례 바꿈은 ①이 못 잡고 ③(옛 코드와 견줌)이 잡는다.
3. **스크래치 전후 비교** — 바꾸기 전 코드와 바꾼 뒤 코드로 같은 씨앗의 실제 라운드를 돌려 스텝마다 견준다. 버킷 커밋 직후, 손잡이 커밋 전에 한다. 명세는 부록 B.
4. **스크래치 «두 번 돌려 견주기»**(검증에서 고침: 처음 안은 `audit`에 assert만 걸었다. `audit`는 후보 빠짐만 세고, `_shove`의 다시 뽑기와 고른 결과는 보지 않는다) — 새 트리 사본에서만 세 함수의 이름을 `_target_of_b`·`_nearest_enemy_b`·`_shove_b`로 바꾸고 원래 이름의 함수를 아래처럼 둔다. 커밋하지 않는다.

   ```gdscript
   func _nearest_enemy(from: Vector2, reach: float, center := Vector2.ZERO, zone := INF, on_wall := false, body := 0.0, air := true):
   	var was := scan_all
   	scan_all = true
   	var want = _nearest_enemy_b(from, reach, center, zone, on_wall, body, air)
   	scan_all = was
   	var got = _nearest_enemy_b(from, reach, center, zone, on_wall, body, air)
   	assert(is_same(got, want), "버킷 _nearest_enemy가 전수와 다르다")
   	return got

   func _shove(e, by: Vector2, bodies: Array) -> void:
   	var was := scan_all
   	var p0: Vector2 = e.pos
   	scan_all = true
   	_shove_b(e, by, bodies)
   	var want: Vector2 = e.pos
   	e.pos = p0  # 움직이는 몸 쪽 세대 수만 오른다. bodies 쪽 버킷은 그대로다
   	scan_all = was
   	_shove_b(e, by, bodies)
   	assert(e.pos == want, "버킷 _shove가 전수와 다르다")
   ```

   `_target_of`도 같은 꼴이다(`_engage`는 같은 대상이면 아무것도 바꾸지 않고 `_gate_or_base`는 `via`를 같은 값으로 둘 뿐이라 두 번 불러도 된다 [추론: 두 함수를 읽음]). `audit`의 기본값도 `[0, 0, 0, 0]`으로 두고 놓친 몸을 세는 줄에 `assert(false, "버킷이 몸을 놓쳤다")`를 더한다. 이 사본으로 `EVAL_FULL=1 pytest`와 부록 B 시나리오(새 트리 쪽)를 돌린다. 다르면 그 EV·그 스텝이 런타임 오류로 빨갛게 난다. 걸리는 시간이 늘어 스위트 하나의 180초 상한(`tests/eval/conftest.py`)에 걸리면 그 스위트만 `runner.gd`로 따로 돌린다.
5. **망가뜨려 보기**(검증에서 더함 — P1은 락 뒤에 «객체는 같지만 부를 때마다 다시 자르는» 변형이 통과해 EV1125를 개정했다) — 구현 뒤 새 트리 사본에 변형을 하나씩 넣고 적힌 시험이 빨갛게 나는지 본다. 안 잡히면 그 시험을 고친다(락 뒤면 개정 행).

   | 변형 | 잡아야 할 시험 |
   |---|---|
   | `pos` setter가 세대 수를 안 올린다 | EV+2 ①④, 유닛 `test_stale_after_outside_write` |
   | `radius` setter가 세대 수를 안 올린다 | EV+2 ③ |
   | 배열 크기 견줌(`ix.n != arr.size()`)을 뺀다 | EV+2 ② |
   | 큰 몸 목록(`big`)을 후보에 안 넣는다 | 유닛 `test_candidates_cover_brute_force`, EV+1(슬라임 킹) |
   | `_shove`의 다시 뽑기를 뺀다 | 유닛 `test_shove_matches_full_scan`(한 줄로 붙어 선 몸). Python 스크래치에서는 36,000번 가운데 94번 갈렸다 |
   | `ids.sort()`를 뺀다 | 유닛 `test_target_ties_keep_array_order` |
   | `BUCKET_PAD`를 −0.5로 둔다(후보를 좁힌다) | EV+1·EV+3의 놓친 몸 수 |
   | `_near`가 늘 모든 번호를 준다(버킷을 안 쓴다) | EV+3의 비율 |

보고에는 견준 스텝 수·시나리오와 «차이 0»(또는 처음 갈린 스텝과 몸), 변형마다 잡은 시험을 적는다. 승패·생존은 적지 않는다.

### 7.4 성능을 기능 검증으로 보기(승패는 재지 않는다)

- 저장소: EV+3(후보 수 비율, 결정적).
- 스크래치 `stepbench.gd`(headless): 문서와 같은 합성 판(시험 스테이지, 집 6채·타워 27개, 체력 1e9인 용병과 적을 정문 앞에서 맞붙임, `merc_cap`을 정해 상한을 뗌)을 (용병, 적) = (28, 200)·(100, 200)·(150, 300)·(200, 400)로 만들어 60스텝 뒤 300스텝의 `step` 시간을 **옛 트리(부록 B의 old)와 새 트리**에서 잰다(평균·중앙값·95%). `scan_all` 켬은 참고로만 적는다 — 그 길은 물을 때마다 `range()` 배열을 만들고 번호로 돌아 옛 코드보다 느리고, 그것과 견주면 이득이 부풀려진다(검증에서 고침). 볼 것: ① 150·300에서 새 트리가 옛 트리보다 뚜렷이 작다(문서의 PC에서는 71 → 27ms였다. 그것은 문서의 스크래치 구현으로 잰 값이고 이 의사코드의 값이 아니다 [추론]. 이 환경의 절대값은 견주지 않는다) ② 28·200에서 새 트리가 옛 트리보다 크지 않다 ③ 영웅 3·적 50 같은 작은 판에서 느려지지 않았다 ④ 뭉친 판(용병 150을 정문 앞 8×7칸에, 적 300을 그 남쪽 16×8칸에 — P6 전의 모습)에서도 새 트리가 작다 ⑤ 기병 20을 섞은 150·300 판에서도 그렇다(§9 위험 4: 한 스텝에 양쪽이 번갈아 서로를 옮기면 다시 담기가 잦다). 안 나오면 `_near`의 갈래 기준·SLACK·BUCKET·정수 열쇠를 고른다(행동과 무관해 EV는 그대로다).
- 전체 pytest 걸린 시간을 전후로 적는다(작은 판마다 다시 담는 비용이 평가 시간을 늘리지 않았나).
- U9 판정은 하지 않는다. 문서 어림으로 P7 뒤에도 150·300의 편집기 프레임 합은 약 50ms(그리기 23~25ms가 남는다)라 목표 30fps에 못 미친다 [문서의 추론]. 보고에 «U9는 그리기 PR 뒤에 닿는다»로 적는다.

«어떻게 걸리나»: S = setter가 세대 수를 올린다 · N = 배열 크기가 달라진다 · 둘 다면 S+N.

검증에서 다시 셈(HEAD `f76bcbe`): battle.gd에서 `pos`·`radius`에 쓰는 줄과 `set(…)` 줄은 66줄이고(주민·장판·깃털·투사체 포함) 모두 속성 대입이나 `set()`이라, `Unit`·`Enemy`의 것은 빠짐없이 setter를 지난다. `units`·`enemies`를 바꾸는 줄은 18곳(`append` 7·`erase` 8·`clear` 3)과 `save.gd#apply`의 `assign` 하나다. 정렬·뒤섞기·번호로 바꿔 넣기는 없다. 저장소의 다른 코드에서는 그림 평가의 `b.enemies.erase` 8곳뿐이다. 아래 표는 그 줄들을 길로 묶은 것이고, 표에서 빠진 길이 있어도 setter·배열 크기에 걸린다.

- `_move`의 줄어듦(S236, 슬라임 킹): 스텝마다 `e.radius`를 넣는다 → S.
- `_turn`(둘째 형태로 바뀜)·`Enemy._init`·`Unit._init`의 `set(key, …)`, 테스트 모드 `tuning.gd#_match` → S.

### A.4 버킷과 무관한 자리 쓰기(건드리지 않는다)

주민(`_place`·`_split`·`_carry_to`·`_set_down`의 주민 가지), 장판(`_zones`의 `z.pos`), 깃털(`_quills`), 투사체(`_shoot`·`_fly`·`_glide`), 쓰러진 탈것의 몸(`_break`의 `body` — 적 배열에 들지 않는다. 세대 수만 오른다).

### A.5 걸리지 않을 수 있는 꼴(지금 코드에는 없다)

«그 편의 버킷에 묻고 → 이미 있던 몸을 `pos`를 안 건드리고 빼고 → 다른 이미 있던 몸을 `pos`를 안 건드리고 넣고 → 다시 묻는다». 지금 넣는 길은 모두 새로 만들거나(`_init`) `pos`를 먼저 넣는다(`_return_hero`·`_come_home`). 이 꼴을 새로 쓰는 코드는 세대 수를 직접 올린다(§3.1 (바)).

## 부록 B. 스크래치 전후 비교 하네스(동치 검증. 난이도 측정이 아니다)

```
S=<스크래치>/p7 ; mkdir -p "$S/old"
git archive <P7 시작 커밋> | tar -x -C "$S/old" && cp -r .godot "$S/old/"     # 옛 코드(godot 스킬 «바꾸기 전후 비교»)
timeout 900 "$GODOT" --headless --path "$S/old" -s "$S/twin.gd" -- <시나리오> <씨앗> <스텝> "$S/old_<시나리오>.txt"
timeout 900 "$GODOT" --headless --path .        -s "$S/twin.gd" -- <시나리오> <씨앗> <스텝> "$S/new_<시나리오>.txt"
cmp "$S/old_<시나리오>.txt" "$S/new_<시나리오>.txt"     # 같아야 한다. 다르면 처음 다른 줄이 갈린 스텝이다
```

`twin.gd`(extends SceneTree, 두 트리에서 같은 파일을 쓴다):

- 판: `load("res://src/main.gd").stage()`에 `seed`, `base_hp` 1e9(판이 끝나지 않게), `merc_cap` 150(두 트리의 상한을 같게), `heroes`(최대 레벨)를 덮는다. 영웅은 오토를 모두 켠다(`h.auto[칸] = true`). 승패·생존은 찍지 않는다.
- 스텝마다 한 줄: `<스텝> <state> <gold> <units 수> <enemies 수> <hash>`. hash는 유닛 목록과 적 목록을 차례대로 [종류, pos.x, pos.y, hp, on_wall, cooldown, 길 칸 수]와 적의 [붙잡은 유닛의 번호, 노리는 칸, 예고 id]를 이어 붙인 배열의 `hash()`, 거기에 거점·성곽 체력 합.
- 다르면 그 스텝에서 처음 다른 몸을 풀어 찍는 둘째 실행 모드를 둔다.

시나리오(모두 `dt` 0.05):

| 이름 | 판 | 넣는 명령 | 덮는 길 |
|---|---|---|---|
| real1 | 1라운드 그대로(슬라임·큰 슬라임·슬라임 킹, `data/waves/test_stage.tres`). 아이아스·실비아·이그니스, 용병 40(여덟 종 섞음)을 정문 앞에, 타워 여섯 | 준비 단계마다 `start_battle`. 100스텝마다 영웅 `dash`, 200스텝마다 용병 절반 `order_move`(두 지점 번갈아) | 슬라임 분열, 큰 몸(슬라임 킹), 처치·쓰러짐·부활, 대시, 방패 밀치기 넉백, 걷다 막힘 |

- 각 6,000스텝(판이 먼저 끝나면 거기까지). `mass`는 3,000스텝이다(옛 트리는 이 수에서 한 스텝이 70ms를 넘는다 — `timeout 1800`). 씨앗 둘(7, 11).
- 통과 기준: 모든 시나리오·씨앗에서 `cmp`가 같다. 보고에 시나리오마다 견준 스텝 수와 그 판에서 일어난 일의 수(쓰러진 적·아군, 분열로 나온 적, 대시, 들림)를 적는다 — 승패는 적지 않는다.
- 같은 하네스를 새 트리에서 `scan_all`을 켠 판과 끈 판으로도 한 번 돌린다(옛 트리 없이 되는 빠른 판). twin.gd는 `scan_all`을 판에 그 칸이 있을 때만 넣는다(`if "scan_all" in b`) — 옛 트리에는 없다(검증에서 더함).
- 프로세스 하나에 판 하나만 만든다. 판이 둘이면 세대 수가 섞여 낡음이 가려진다(§2.3).
