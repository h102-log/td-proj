# P7 검토 관점 셋 (2026-11-16에 돌리지 못했다 — 서브에이전트가 모델 사용 한도로 실패)

대상: `p7.patch`를 적용한 트리. 구현의 주장은 «버킷은 보는 몸 수만 줄이고 `_target_of`·`_nearest_enemy`·`_shove`의 결과는 전수 루프와 같다»다. 검토는 읽기·실행만 하고, 확인된 지적만 고친 뒤 전체 pytest를 한 번 돌린다. 승패·생존은 읽지 않는다(난이도 측정은 사용자 몫).

## 1. 동치 — «행동이 그대로»를 깨는 경우 찾기
1. 차등 시험을 새로 쓴다(구현이 쓴 시험을 다시 돌리는 것으로 끝내지 않는다): 무작위 판(아군·적 수십~수백, 뭉친 판·흩어진 판·한 줄로 선 판, 반지름이 1칸을 넘는 큰 몸, 같은 거리 동률, 맵 가장자리·음수 좌표·버킷 경계 위의 몸)에서 세 함수를 버킷 길과 `scan_all` 길로 불러 고른 대상·돌려준 자리를 글자까지 견준다.
2. 낡음: 스텝 사이에 밖에서 `pos` 대입·`set("pos", …)`·`pos.x`만 쓰기·`radius` 바꾸기·`units`/`enemies`에 append·erase·insert·같은 수로 빼고 넣기(계획서 부록 A.5)·배열 통째 바꿔 넣기를 한 뒤 «먼저 묻고 → 바꾸고 → 곧바로 묻기»로 버킷이 낡은 답을 주는지 본다. `src/`·`tests/`·`tools/`에서 Unit·Enemy의 자리·반지름을 쓰는 곳과 `units`·`enemies` 배열을 바꾸는 곳을 grep해 세대 수가 오르지 않는 길이 있는지 본다(정렬·뒤섞기·duplicate·assign·filter로 바꿔 넣기 포함).
3. 세대 수가 클래스 static이라 한 프로세스에 판이 둘일 때(쌍둥이 평가, 저장 불러오기, restart) 낡음이 가려지거나 틀리는지. static이 인스턴스 속성 목록(`save.gd#_fields`·`battle.gd#_body`)에 새지 않는지, 저장 왕복이 그대로인지.
4. 옛 트리(`git archive f76bcbe`)와 새 트리에서 같은 판을 스텝마다 해시로 견준다: 실제 1~6라운드 웨이브, 원정 층들, 슬라임 킹, 기병 돌진 밀기, 보스 넉백 연발, 용병 150명 판. 구현 보고의 시나리오 말고 다른 씨앗·다른 판을 둘 이상 더한다.
5. `_shove`의 다시 뽑기(밀려서 범위를 벗어남)와 «이미 지난 번호 건너뛰기»가 원래 루프의 차례와 같은지 코드로 따지고, 줄지어 선 몸을 따라 길게 미끄러지는 판으로 확인한다. 봇의 코드 생성 하위 클래스(`tools/balance/autoplay.gd`가 `_target_of`를 덮어쓰는 곳)가 그대로 도는지.

## 2. 장부 — SPEC·EVAL
1. gate 위반이 §3.1 «범위 밖»뿐인지.
2. «→ 2026-11-16 변경»이 CLAUDE.md 규칙대로인지: 중심 문장은 S25 하나(우선 구절이 인구에만 걸리고 타워 상한 S299·I246의 4·4·28을 덮지 않는지), U9 «→ 변경»(번복 조건 칸의 «5.1에서 확정한다(사용자 2026-10-13)»가 지워지지 않았는지), I225·I246은 수치만 제자리에서 고쳤는지. 수치가 틀려졌는데 안 고친 문장이 없는지(SPEC.md에서 «인구»·«4명»·«28»·«거점 몫»·«집마다»·«POP_BASE»·«60fps»·«100명»을 모두 찾아 대조). 사용자 근거가 있는 결정(S25 2026-11-04, U9 2026-10-13, S365 2026-11-12의 머리 줄 «인구 n/m»)과 부딪히는 곳이 SPEC 글에 드러났는지.
3. 새 문장 I305의 자리(§2.2 «플레이 후기 4» 묶음)·꼴·`[추론]`·근거, 글이 실제 코드(버킷 크기·큰 몸 기준·낡음 규칙·`BUCKET_MIN` 16)와 맞는지.
4. 새 EV1133~EV1137과 고친 EV(EV742·EV809·EV1094·EV1101 등)마다 본표 측정 글의 수치·조건을 테스트 코드와 한 줄씩 대조한다. 문턱(후보 비율 0.15)이 락에 박혔는지. 측정이 약해 틀린 구현도 통과하는 EV를 망가뜨려 보기로 찾는다(setter의 세대 수 올리기를 빼거나, `_shove` 다시 뽑기를 빼거나, 큰 몸을 버킷에 넣었을 때 어느 EV·유닛 시험이 빨개지는지 — 하나도 안 빨개지면 지적이다).
5. 개정 행: 묶기 규칙, 사유 글에 다른 EV 번호 없음, 날짜.
6. SPEC 문장 한 줄·덧붙이기, §3.1 안 건드림.

## 3. 인구·화면·저장·회귀
1. `POP_BASE` 30·집 `pop` 20: 마을이 있는 판의 배치 상한이 집 0~6채에서 30~150인지, 상한에 닿으면 구매가 거부되는지, 영웅은 세지 않는지, 타워 상한(4·4·28)이 그대로인지를 스크래치 판으로 확인한다.
2. 옛 저장: 집 pop 4가 저장된 꼴을 만들어 불러 상한이 데이터 값(집 6채면 150)으로 맞는지, 새 저장 왕복(snapshot → apply → snapshot)이 같은지, 집이 아닌 구조물의 저장 값이 바뀌지 않는지.
3. 화면을 xvfb로 캡처해 직접 열어 본다(한국어·영어): 위 띠 아래 인구 칸(폭 58)에 «인구 150/150»이 테두리에 닿지 않는지, 타워 칸이 x 66으로 밀려 옆 칸·맵 요소와 겹치지 않는지, 거점 패널 머리 줄 «n/m»이 «↶» 등과 겹치지 않는지, 인구 툴팁 «상한 150(거점 30 + 집 6채 × 20)» 꼴, 한 자리·두 자리·세 자리 수 모두. 인구 칸을 넓혀 달라진 다른 칸의 클릭 영역·EV 좌표가 있는지(`tests/eval/gd/*.gd`에서 60·52 같은 좌표 상수 grep).
4. 계획서 7.1의 스위트와 `.brain`이 뽑은 영향 스위트를 차례로(`EVAL_JOBS=1`) 돌리고, C 평가에 닿는 스위트(hud·keep 등)는 `EVAL_FULL=1`로 돌린다. 유닛 시험 전체. 스위트 실행 시간이 HEAD보다 눈에 띄게 늘었는지(스위트 상한 180초 — setter·다시 담기 비용).
5. `tools/balance/autoplay.gd`·`tools/bench`·`tools/play`가 문법 오류 없이 도는지(승패는 읽지 않는다). `locale/en.po` 누락·고아(`test_locale`).
