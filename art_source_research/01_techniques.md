# 01. 기법 — Claude가 코드로 도트 아트를 만드는 방법

질문 1에 답한다. Claude가 코드로 16px 스프라이트·애니메이션 프레임·타일셋·UI를 만드는 방법은 무엇이고, 자산 종류마다 어느 방법이 맞는가. 렌더한 PNG를 Claude가 다시 보고 고치는 루프로 품질이 얼마나 오르는가.

확인 날짜는 모두 2026-10-11이다. 표기법은 [README](README.md#표기와-신뢰도)에 있다.

## 요약

- Claude는 이미지를 이해만 하고 만들지는 못한다 [T-01]. "Claude가 아트를 만든다"는 말은 Claude가 PNG를 굽는 코드와 데이터를 쓴다는 뜻이다.
- 지금 환경에서 바로 되는 방법은 Python+Pillow로 "팔레트 문자 격자 → PNG"를 굽는 방식이다. 추가 설치 없이 돌았고, Claude Code의 Read 도구로 확대 미리보기를 열어 검토할 수 있었다 [T-02].
- Aseprite CLI·MCP는 편의 기능이 많다. 하지만 Aseprite를 사야 하고, 문자 격자보다 품질이 낫다는 근거는 없다(추론). 사람이 손으로 보정할 때만 쓴다.
- SVG는 16px 도트에 이점이 없다 [T-10] [T-11].
- 이펙트·피격 번쩍임·팔레트 변종·체력바는 Godot 셰이더와 파티클로 처리해 그릴 양을 줄인다 [T-16] [T-17].
- 렌더→검토 루프는 객관적 오류를 줄인다는 근거가 있다 [T-20] [T-21]. 미감을 스스로 끌어올린다는 근거는 약하다 [T-22] [T-23]. 픽셀아트나 Claude를 대상으로 루프 효과를 잰 연구는 찾지 못했다 [T-24].

## 1. 방법별 설명

### A. Python+Pillow 문자 격자 — 권장

- 방식: 팔레트를 `{'K': 외곽선, 'S': 갑옷 어두움, ...}`처럼 정하고, 16줄짜리 문자열 배열을 RGBA PNG로 굽는다. 검토용 이미지는 `Image.NEAREST`로 ×16~×24 확대하고 1px 격자를 덧그린다.
- 직접 시험: Python 3.12.10, Pillow 12.3.0에서 16×16 영웅 1장, ×24 격자 미리보기(384×384), 4프레임 스트립 ×20(1280×320)을 만들었다. 원본 16px은 Read로 열어도 점 덩어리라 판독할 수 없었다. ×24 격자 이미지에서는 행·열 단위로 색 배치를 대조할 수 있었다. 한 번 시험한 결과다 [T-02].
- 같은 계열 선례:
  - Pixel Art Bench는 LLM에게 2~10색 팔레트와 24×24 숫자 인덱스 격자를 JSON으로 받는다. 토큰을 아끼려는 형식이다 [T-25].
  - Claude Code용 Pillow 기반 픽셀아트 스킬이 공개돼 있다. 결과 품질을 평가한 자료는 없다 [T-28].
  - 다른 개발자는 팔레트를 고정하고 코드에 인덱스만 기록하는 방식으로 Claude Opus 5에게 픽셀아트를 굽게 했다 [Q-12].
- 장점(추론): 같은 입력이면 같은 출력이 나온다. 텍스트라 git diff로 프레임 간 변경을 볼 수 있다. 설치가 필요 없다.
- 약점(추론): 실루엣과 형태감은 Claude가 격자를 머릿속에 그리는 능력에 달렸다. 32px이면 그릴 픽셀이 4배다.

### B. Aseprite CLI Lua / Aseprite MCP — 보류

- `--batch`는 명령줄 옵션만 처리하고 끝난다. `--script`로 스크립트를 실행하고 `--script-param`으로 값을 넘긴다 [T-06].
- Lua Image API에 `drawPixel`, `drawImage`, `saveAs`, `resize(method='rotsprite')`, `flip()`이 있다 [T-07].
- GitHub에 Aseprite MCP 서버가 여럿 있다. 모두 Aseprite를 따로 설치해야 한다 [T-09].
  - willibrandon/pixel-mcp: Go, MIT. 팔레트·디더링·프레임/태그·시트 내보내기를 제공한다.
  - diivi/aseprite-mcp: Python 3.13 이상, 도구 104개, 어니언스킨 렌더. README가 "×8로 내보내기→검토→수정" 루프를 권한다. 라이선스 표기가 없다.
- 가격: Steam 한국 스토어 ₩21,000, 확인 시점 할인 없음. 체험판은 저장할 수 없다 [T-08] (1차 출처 미확인). 출처: https://store.steampowered.com/app/431730/Aseprite/ , https://www.aseprite.org/trial/ (확인 2026-10-11)
- 판단(추론): 품질은 결국 Claude가 어디에 픽셀을 두느냐로 정해진다. 그래서 A와 같은 한계를 가진다. 우위는 어니언스킨·rotsprite·시트 내보내기 같은 편의뿐이고, 이것도 Pillow 스크립트로 대신할 수 있다. 사용자가 손으로 보정하기로 할 때만 살 가치가 있다.

### C. SVG 래스터화 — 쓰지 않음

- `shape-rendering="crispEdges"`는 렌더러가 안티앨리어싱을 끌 "가능성이 크다"는 수준이다. 곡선·대각선은 매끄러움을 잃고, 결과가 렌더러마다 다르다 [T-10].
- 픽셀마다 `<rect>`를 쓰는 SVG는 문자 격자와 정보량이 같으면서 장황하다. 래스터화 도구(cairosvg·resvg·Inkscape)는 지금 모두 미설치다 [T-11].

### D. Godot 안에서 — 런타임 연출 담당

- 헤드리스 생성: Godot 4.7에서는 `Image.create_empty`(create는 deprecated), `set_pixel`, `blit_rect`, `flip_x`, `resize(INTERPOLATE_NEAREST)`, `save_png`를 쓴다. `--headless --script`로 실행하고, 스크립트는 SceneTree나 MainLoop를 상속해야 한다 [T-12].
- 다만 Pillow로 같은 일이 되고 godot 실행 파일이 PATH에 없다. 굽기는 Python이, 런타임 연출은 Godot이 맡는 쪽이 단순하다(추론).
- 셰이더: 팔레트 교체(팔레트 이미지의 행 = 변종), 피격 번쩍임, 외곽선 예시가 godotshaders.com과 Juice Shaders Lite(MIT)에 있다 [T-17]. 셰이더별 라이선스는 확인하지 않았다. 수십 줄짜리라 Claude가 직접 쓰면 이 문제를 피한다(추론).
- 파티클: GPUParticles2D가 기본 권장이다. 텍스처 없이도 점을 방출하고, Explosiveness로 순간 분출을 만든다 [T-16]. 피격 불꽃, 사망 먼지, 건설 먼지를 아트 없이 처리할 수 있다(추론).
- TileSet terrain: Match Corners and Sides / Match Corners / Match Sides 세 모드가 있다. Use Texture Padding을 켜면 타일마다 1px 투명 테두리를 더해 번짐을 막는다 [T-13].

### E. 절차적 생성 — 타일과 변종

- 오토타일 장 수: 4비트 16장, blob 47장, 듀얼 그리드 16장(빈 타일 빼면 15장), 쿼터 방식은 고유 모양 5개 [T-14].
- 들판에는 꼭짓점 기준 16장 세트(듀얼 그리드 또는 Match Corners)가 코드 생성에 맞다. 장 수가 적고 꼭짓점 4개의 지형 값만으로 타일이 정해지기 때문이다 [T-15].
- 바닥 변종(추론): 시드를 고정한 난수로 풀·돌·흙 얼룩 몇 픽셀을 흩어 같은 바닥의 변종 3~4장을 만든다. 두 색 경계는 Bayer 같은 순서형 디더링으로 부드럽게 한다. pixel-mcp도 디더링 도구를 제공한다 [T-09].
- 대칭 스프라이트 생성기(Bollinger 방식)는 무작위 격자를 반사해 대칭 스프라이트를 만든다 [T-18]. 결과가 무작위라 고르는 수고가 든다. 적 5종은 Claude가 의도를 갖고 그리는 편이 낫고, 생성기는 아이콘·잡몹 변종을 대량으로 만들 때만 고려한다(추론).

### F. 애니메이션 구성

- 작은 스프라이트의 4프레임 걷기는 접지→통과→반대 접지→통과다. 몸통을 1~2px 위아래로 흔들고, 두 접지 프레임의 머리 높이를 같게 하며, 팔은 다리와 반대로 흔든다. 32px 이상은 6~8프레임을 권하는 가이드가 있다 [T-19].
- 코드화 요령(추론):
  - 기본 포즈 1장에 프레임별 "다리 행 교체 + 몸통 y 오프셋" 차분만 적는다. 머리·몸통 픽셀을 다시 쓰지 않으므로 프레임 사이 일관성이 구조적으로 보장된다.
  - 좌우는 Godot `flip_h`로 처리하고 한 방향만 그린다.
  - 적 변종과 진영 색은 팔레트 교체로 만든다.
  - 사망은 3프레임(기울기→쓰러짐→셰이더 dissolve 또는 페이드)으로 한다.
  - 공격은 2~3프레임에 번쩍임 셰이더와 파티클을 더한다.
- 주의: 같은 파츠를 코드로 변형해 일관성을 얻어도 동작 품질은 따로다. 사인 함수로 만든 걷기가 중복 프레임을 낸 사례가 있다 [Q-13].

| 폰트 (한국어·영어) | 만들지 않는다. OFL 비트맵 폰트를 쓴다([06](06_fonts_and_capsule.md)) | 수천 글자가 필요하다 [T-27] |

## 3. 렌더→검토 반복 루프: 효과와 한계

### 근거

- 도움이 된다는 근거:
  - MatPlotAgent(플롯 코드 생성)에서 시각 피드백을 빼면 GPT-4 점수가 61.16에서 53.44로, GPT-3.5가 47.51에서 41.57로 떨어졌다. 약 6~8점 차이다 [T-20].
  - PlotGen은 시각 피드백 에이전트를 빼면 10~15% 떨어진다고 보고했다. 본문은 열람하지 않았다 [T-21].
  - 둘 다 글자 겹침·요소 누락 같은 객관적 오류를 고친 사례다(추론).
- 한계에 대한 근거:
  - Perlman 외(2026, Qwen3.5 9B·27B, Claude 미포함)는 범용 VLM의 SVG 반복 수정이 시각 품질에 "inconsistent effect"를 준다고 보고했다. 단일 생성 CLIP 점수(0.255)가 반복 변형(0.205~0.246)과 같거나 높았다 [T-22].
  - 렌더 피드백으로 SVG 품질을 올린 최근 연구는 학습(Visual Self-Feedback, SFT+DPO)을 전제로 한다. 범용 모델에 루프를 그대로 붙이면 최적이 아니라고 한다 [T-23].
  - 코드로 픽셀아트를 굽은 개발 사례에서 Claude는 PNG를 보고 초상화 결함 11건을 스스로 찾았다. 큰 조각의 회전 결함 4건은 하나도 찾지 못했다 [Q-13].
- Claude 시각 기능의 공식 한계:
  - 저품질·회전되었거나 200px 미만인 아주 작은 이미지는 환각하거나 실수할 수 있다 [Q-07]. "200px 이상으로 확대하라"는 권고는 문서에 없고, 이 경고에서 끌어낸 추론이다 [Q-07].
  - 좌표 출력은 근사치다. 작은 물체가 많으면 개수 세기가 부정확하다. GIF는 첫 프레임만 쓴다 [T-04].
  - 이미지는 28×28px 패치 단위로 처리한다. Claude 4.7 이후 모델은 긴 변 2576px, 그 밖은 1568px을 넘으면 축소된다 [T-03].
- 찾지 못함: 픽셀아트나 Claude를 대상으로 루프 효과를 정량화한 연구. Pixel Art Bench의 Claude 결과(확인 시점에 결과표가 비어 있음) [T-25].

### 예상 효과 (추론)

- 잘 잡히는 것: 엉뚱한 색, 끊긴 외곽선, 한쪽만 긴 팔다리, 대칭 깨짐, 프레임마다 다른 머리 높이, 타일 경계 단절, 크기·위치 오프셋.
- 잘 안 잡히는 것: 실루엣이 "무엇으로 읽히는가", 명암 덩어리의 미감, 프레임 사이 미세한 동작 품질, 1픽셀 단위 미세 조정.
- 2~3회 반복한 뒤로는 개선이 작을 것으로 본다 [T-24]. 에셋마다 반복 상한을 정해야 시간과 사용량을 통제할 수 있다.
- 결론: 루프는 오류 제거용으로 기대한다. 미감은 사용자가 판정하고 자동 검사로 보완한다.

### 운영 요령 (추론, [T-05] 바탕)

1. 원본 16px은 그대로 보여 주지 않는다. ×16~×24 NEAREST 확대에 1px 격자, 4px마다 진한 선, 행·열 번호를 넣는다. ×28이면 원본 1픽셀이 패치 하나에 맞는다 [T-05].
2. 한 장의 긴 변을 1568px 이하로 둔다. 16px×8프레임×12배 = 1536px까지 한 줄에 들어간다 [T-05].
3. 애니메이션은 GIF 대신 가로 스트립, 어니언스킨 겹침, 프레임 차이 히트맵으로 보여 준다 [T-05].
4. 타일은 3×3과 8×8로 반복 배치한 이미지를 함께 본다 [T-15].
5. 게임 실제 배율(640×360 기준 ×3)의 1:1 미리보기도 함께 본다. 확대에서 괜찮아도 실제 크기에서 안 읽히는 문제를 잡기 위해서다.
6. 시각 검사를 자동 검사(lint)로 보완한다: 팔레트 밖 색, 반투명 픽셀, 프레임 크기, 타일 가장자리 일치, 프레임 사이 변경 픽셀 수. 눈이 근사치인 영역(좌표·개수)은 코드가 판정한다 [T-04].
7. 이미지는 숫자 검사를 먼저 돌린 뒤 가끔만 보여 준다. 사용량과 정확도 모두에 유리하다 [Q-23]. 같은 화면 묶음을 PNG로 보면 약 29,000토큰, ASCII 덤프로 보면 약 240,000토큰이었다는 사례가 있다 [Q-12].
8. 사용자가 고른 참고 이미지(예: 에셋팩 미리보기)를 같은 배율로 옆에 둔다.

## 4. 지금 환경에서 쓸 도구 체인

추가 설치 없이 쓰는 Python+Pillow 단일 체인을 제안한다 [T-29].

```
art/
  palette.json        # 공용 팔레트 16~24색. 모든 에셋이 공유해 자산 간 일관성을 지킨다
  src/units/hero.txt  # 기본 포즈 격자 + 프레임 차분 + 애니 정의
  src/tiles/...       # 절차 생성 파라미터(시드, 색 비율)
tools/
  bake.py     # 격자 → 1× RGBA PNG, 스트립·시트, 팔레트 변종, 오버레이 합성
  preview.py  # ×N 확대 + 격자·좌표, 컨택트 시트, 3×3·8×8 타일, 어니언스킨, 1:1 실배율
  lint.py     # 팔레트·반투명·크기·타일 가장자리·프레임 차분 검사. 실패하면 종료코드 1
→ Godot res://art/ → AnimatedSprite2D(flip_h), TileSet terrain(Match Corners),
  직접 쓴 셰이더(팔레트 교체·피격 번쩍임·외곽선), GPUParticles2D
```

- 루프: Claude가 격자를 고친다 → `bake.py && lint.py && preview.py` → Read로 미리보기를 연다 → 다시 고친다. 에셋당 최대 3회(추론, [T-24]의 수확 체감 근거).
- Aseprite와 MCP 서버는 사용자가 손으로 보정하기로 할 때만 쓴다. cairosvg·resvg는 쓰지 않는다 [T-29].
- 텍스트가 원천이라 커밋 diff로 변경 이력을 추적한다. 에셋팩에 팔레트 교체·오버레이를 더하는 하이브리드에도 같은 체인을 쓴다(추론).
- 가정: 기준 칸 16px, 유닛은 측면 한 방향(좌우는 `flip_h`). 4방향 이동이 필요하면 유닛 프레임 수가 약 2~3배로 는다(추론).
